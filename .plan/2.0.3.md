Context:
"Partner Center Alternative Names" is a Chrome extension (content script) that
runs on the Partner Center customer list page
(https://partner.microsoft.com/dashboard/v2/customers/granularadminaccess/list)
and injects an "Alternative Name" column/values by matching rows to customer
IDs.

Confirmed facts about the page (verified by live inspection, not assumption):
- The customer name in each row is NOT a plain <a href> link. It is rendered
  as a custom web component button:
  <customersvcadmin_he-button appearance="link" type="button">{name}</customersvcadmin_he-button>
  nested inside multiple layers of shadow DOM (the page uses "he-*" custom
  elements throughout, e.g. he-shell, he-layout, customersvcadmin_he-data-grid).
- Each row is <tr id="row-{customerId}">, and the name cell is
  <th id="cell-displayName-{customerId}"> containing
  <slot name="displayName-{customerId}">. The extension's existing
  alternative-name logic must already resolve this same customerId per row
  (it needs it to render the "Alternative Name" column) — reuse that existing
  row/ID resolution code rather than re-deriving it.
- Clicking the name button triggers the SPA's own internal navigation and
  changes the browser URL to:
  https://partner.microsoft.com/dashboard/v2/customers/{customerId}/adminrelationships
  This was confirmed by manually clicking a row and observing the resulting
  tab URL.
- The route https://partner.microsoft.com/dashboard/v2/customers/{customerId}/servicemanagementpage
  is a valid sibling route within the same customer-detail SPA shell (same
  left-nav appears: Devices, Users and licenses, Admin relationships, Service
  management, Service requests, Account). So redirecting there is a pure path
  swap — same customerId, no additional API calls or lookups required.

Task:
Add a boolean setting "Keep default link behaviour" to the extension's
options UI, default = true (checked), persisted the same way other options
are stored (chrome.storage.sync or whatever the extension already uses).

Behaviour:
- When true (default): no change at all — clicking a customer name works
  exactly as today (navigates to .../adminrelationships).
- When false: clicking a customer name should instead end up at
  .../servicemanagementpage for that same customerId.

Implementation guidance:
Because there is no real <a href> to rewrite, and the button's navigation
is handled by an internal JS click handler on a custom element buried in
shadow DOM, you cannot just change a link attribute. Please verify and pick
the most reliable of these approaches (in this order of preference), testing
directly in the extension dev environment since I could not inspect the
bundled application JS to confirm internals:

1. Preferred — patch history.pushState/replaceState:
   Partner Center is a client-side-routed SPA. Early in the content script,
   wrap window.history.pushState (and replaceState) so that whenever the app
   calls it with a URL matching
   /dashboard/v2/customers/{guid}/adminrelationships, and the option is
   disabled, rewrite the trailing segment to "servicemanagementpage" before
   calling the original function. This avoids touching shadow DOM event
   handling entirely and is likely the most robust single interception point.
   Verify this is actually how navigation happens (vs. a full
   location.assign/reload) before relying on it.

2. Fallback — capture-phase click interception:
   Register a click listener on `document` with `{capture: true}`. Click
   events are composed and cross shadow boundaries, so use
   `event.composedPath()` to detect a click landing on a
   `customersvcadmin_he-button` inside a `cell-displayName-{customerId}` /
   `slot="displayName-{customerId}"` element. Capture-phase listeners on
   document fire before the component's own handler, so
   `event.stopImmediatePropagation()` there can block the SPA's native
   navigation. Then perform navigation yourself using the app's router if
   reachable, or `history.pushState` + a manually dispatched `popstate`
   event, targeting the servicemanagementpage URL for that customerId. Only
   fall back to a hard `location.assign` if the SPA doesn't pick up
   pushState/popstate correctly (this causes a full reload, which is worse
   UX but still correct).

3. Last resort — post-navigation correction:
   Let the click proceed normally, watch for the URL becoming
   .../adminrelationships (via a popstate listener or short polling of
   location.pathname), and if the option is disabled, immediately swap it to
   .../servicemanagementpage via history.replaceState + popstate dispatch.
   Only use this if 1 and 2 don't work, since it can cause a visible flash.

Please implement whichever approach actually works reliably when tested,
add the toggle to the options page, and summarize which interception method
was used and why, plus list all files changed.
