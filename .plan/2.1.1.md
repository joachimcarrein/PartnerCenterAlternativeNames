# v2.1.1 — "Unknown" everywhere: the GDAP token left sessionStorage

**Status: implemented and live-tested against the real Partner Center app —
confirmed working.** Reloading the extension and refreshing the GDAP page
restored the alternative names immediately, with no cache clear or reset
needed. Fix 1 is additionally covered by assertions run against the extracted
functions (see [Verification](#verification)).

## Symptom

The Alternative Name column showed `Unknown` for most customers, where those
same customers previously showed a value. A page refresh did not help. Custom
(user-set) names were unaffected and still displayed correctly.

## Evidence

Captured from the live GDAP page, extension isolated world, with the grid fully
rendered (10 rows):

```json
{
  "domainCacheEntries": 71,
  "displayNameCacheEntries": 0,
  "expiry": "2026-10-10T14:12:05.990Z",
  "expired": false,
  "liveDomainMap": 71,
  "liveNameMap": 0,
  "overrides": 6,
  "authContextPresent": true,
  "gdapTokenPresent": false,
  "visibleRows": 10,
  "visibleRowsInDomainCache": 3,
  "visibleRowsInNameCache": 0
}
```

Reading that against the code:

- `domainCacheEntries: 71` — the Partner Center half is **healthy**. The domain
  cache was never the problem.
- `visibleRowsInDomainCache: 3` of 10 — only 3 visible customers are transacted
  and therefore have a domain at all. That is normal and expected
  (constraint 5): `/v1/customers` only returns transacted customers, so the
  other 7 have **always** depended on the GDAP `displayName` fallback.
- `displayNameCacheEntries: 0` — that fallback has no data whatsoever.
- `gdapTokenPresent: false` — `sessionStorage.CustomerSvcAdminKey` does not
  exist, so `getGdapToken()` returned null and `fetchDisplayNames()` bailed
  before issuing a single request.
- `Unknown` rather than `—` confirms `loadState === 'ready'`: the 71 domains
  are enough to make the load "succeed", so the failure never surfaced as an
  error state — it just quietly degraded 7 of every 10 rows.

The decisive detail is that the token was absent **while the grid was already
rendered**. The page cannot have rendered that grid without calling
`delegatedAdminGdapCustomers` itself, so it *has* a valid token — it simply no
longer leaves it in `sessionStorage` under the name the extension reads.
This is therefore **not** a `document_idle` timing race, and no amount of
retrying or waiting would have fixed it.

## Root cause

`getGdapToken()` had exactly one source of truth:

```js
const token = sessionStorage.getItem('CustomerSvcAdminKey');
if (!token) return null;   // -> fetchDisplayNames() gives up entirely
```

Microsoft stopped populating that key. Every consequence follows from it:

1. `fetchDisplayNames()` returns null on every load, forever.
2. `displayNameCache` stays `{}`.
3. Every non-transacted customer falls through to `Unknown`.
4. Because the domain half still has 71 entries, `loadDomainData()` returns
   true, `loadState` becomes `ready`, and nothing looks broken.

## Fix 1 — an empty cache half is not data

Found while diagnosing; a **separate latent bug**, not the cause of this
report, but it would have made the above permanent and unrecoverable.

`readCache()` gated the domain half on presence, not content — and `{}` is
truthy:

```js
const domains = result && result[CACHE_KEY];
if (!domains || !expiry || Date.now() >= expiry) { /* miss */ }
```

Meanwhile both writers passed `|| {}` for a half whose fetch had failed:

```js
writeCache(domains || {}, names || {});   // loadDomainData()
writeCache(fresh   || {}, names || {});   // rebuildCache()
```

So a failed domain fetch paired with a successful name fetch persisted
`domainCache = {}` **and** pushed `domainCacheExpiry` 30 days out. On the next
load that `{}` read back as a valid cache hit containing zero domains, so
`fetchAllDomains()` was never retried — for 30 days, surviving page reloads.
`rebuildCache()` re-poisoned it on every attempt while reporting `ok: true`, so
the popup's **Rebuild local cache** could not clear it either.

The names half already had this guard (`Object.keys(...).length`); the domains
half never got it.

Changes:

- New `nonEmpty(obj)` helper — truthy only for a non-empty plain object.
- `readCache()` now gates on the shared expiry, then returns each half
  independently, mapping empty to `null`. Its contract changed from
  "`{domains, displayNames}` or `null`" to "always an object, either half
  possibly `null`"; `loadDomainData()` (the only caller) was updated to match.
- `writeCache()` now writes **only** the halves it was actually given. A caller
  whose fetch failed passes `null`/`{}` and the stored half is left alone
  instead of being overwritten with `{}`. Both halves empty = no write at all.

Side benefit: `writeCache(null, names)` is now a valid names-only write, which
fix 2 relies on.

## Fix 2 — take the token from the request the page already makes

Rather than guess at a new storage key (which would break again the next time
Microsoft moves it), capture the token from the page's own outgoing request.

`search-inject.js` already runs in the MAIN world at `document_start` and
already wraps `XMLHttpRequest.prototype.open` and `window.fetch`, and already
filters on `TARGET_HOST = api.partnercustomersecurity.microsoft.com` — the exact
host whose token is needed. Capturing the `Authorization` header there is
incremental, and correct by construction: it is by definition the token that
host accepts.

In `search-inject.js`:

- `isTargetUrl(url)` — hostname check shared with the rewriter.
- `XMLHttpRequest.prototype.open` stamps `this.__altnameIsTarget` so the new
  `setRequestHeader` wrapper knows which request's `Authorization` to read.
  (The header cannot be read in `open` — it is not set yet.)
- `window.fetch` reads the header via `readAuthHeader()`, which handles all
  three shapes fetch accepts (`Headers`, array of pairs, plain object).
  `init.headers` takes precedence over `input.headers`, since that is what
  actually gets sent when both are supplied.
- `captureToken()` strips the `Bearer ` prefix so the stored shape matches what
  `sessionStorage` used to hold, deduplicates, and posts
  `{ kind: 'GDAP_TOKEN', payload }` over the existing `__altnameBridge`.
- The token is retained and re-published on `REQUEST_TOKEN`, because
  `content.js` loads at `document_idle` and will usually miss the page's initial
  grid request.

In `content.js`:

- `bridgeGdapToken` module state; never persisted to `chrome.storage` (it is as
  short-lived as the sessionStorage one ever was).
- `getGdapToken()` tries `CustomerSvcAdminKey` first (fast path, still works if
  Microsoft brings it back), then the bridged token.
- Bridge listener accepts `GDAP_TOKEN` and, on a *new* value, calls
  `maybeRecoverDisplayNames()`.
- `maybeRecoverDisplayNames()` refetches the names half when a token arrives
  after `loadDomainData()` already gave up, then writes names-only, sets
  `loadState = 'ready'` and re-injects. Guarded three ways: a re-entrancy flag,
  `displayNameMap.size` (nothing to recover), and `loadState === 'pending'` —
  while pending, the in-flight `loadDomainData()` will pick the token up on its
  own attempt, so recovering in parallel would double-fetch.
- `init()` posts `REQUEST_TOKEN` once, for the case where the token was captured
  before this script loaded.
- New debug helper `getTokenStatus()`.

### Why postMessage-ing a bearer token is acceptable here

It looks alarming and deserves the comment it has in both files. It is not a
privilege leak:

- It is the **page's own** token, read out of the **page's own** request. The
  MAIN world already had it; nothing new is exposed to the page.
- The `postMessage` is pinned to `window.location.origin`, so it is not
  delivered cross-origin.
- Only a 12-character prefix is ever logged, matching the existing convention.
- It is never written to `chrome.storage`.

`getTokenStatus()` deliberately returns **booleans and counts only** — never a
token value, never tenant IDs, never override text — so it stays safe to paste
into a shared debugging session.

## Not fixed (deliberately)

- **`fetchSingleDomain()` never persists its result.** Every page load re-fires
  a per-row lookup for each row lacking a domain, and a value it resolves
  vanishes on reload. Fixing it needs care: merging one entry into a missing
  `domainCache` would create a 1-entry cache that then masquerades as a
  complete one and blocks the full fetch for 30 days (the same class of bug as
  fix 1). It must merge only into an already-populated cache and must not touch
  the expiry. Out of scope for a patch release.
- **`Unknown` vs `—`.** With the domain half healthy, a total GDAP failure still
  reports `loadState = 'ready'` and shows `Unknown`, which reads as "this
  customer has no name" rather than "the name lookup is broken". Making that
  honest means per-half load state and user-visible text churn.

## Verification

**Fix 2 — live-confirmed.** Reloaded the extension (↻), refreshed the GDAP page,
and the proper alternative names appeared immediately. Notably **no reset or
cache clear was required**: `displayNameCache` was already empty, and after
fix 1 empty correctly reads as a miss, so the names half was refetched on the
very next load using the bridged token. The `location`-independent capture in
`search-inject.js` therefore fires early enough on a normal page load for
`loadDomainData()` to find a token on its first attempt.

**Fix 1 — verified by assertion**, against the `nonEmpty`/`readCache`/
`writeCache` functions extracted verbatim from `content.js` with a stubbed
`chrome.storage.local`:

- `{}` and `null` are not data; a populated object is.
- A stored `domainCache: {}` with a valid expiry now reads back as `domains:
  null` (a MISS) instead of a 30-day HIT with zero domains — the bug itself.
- A healthy names half is still returned alongside a dead domains half.
- `writeCache(null, names)` leaves a populated `domainCache` untouched and
  writes only the names half.
- `writeCache({}, {})` performs no write at all (the expiry is not touched).
- Regressions: an elapsed expiry still nulls both halves, and fresh populated
  data still round-trips.

To re-inspect state in the browser, in the extension's isolated world:

```js
window._tenantDomainDebug.getTokenStatus()
```

Confirmed shape: `gdapSessionStorage: false`, `gdapBridged: true`, `names` > 0.

Expected `[AltName]` log sequence:

```
[AltName/net] Captured GDAP token from the page request. Prefix: eyJ0eXAiOiJK
[AltName] CustomerSvcAdminKey missing from sessionStorage — trying the bridged token.
[AltName] GDAP token OK (captured from the page request). Prefix: eyJ0eXAiOiJK
[AltName] GDAP fetch complete: <N> display names across <P> page(s).
```

If `gdapBridged` ever goes back to `false`, the page is not issuing that request through
`window.fetch`/`XMLHttpRequest` (e.g. it moved to a service worker), and the
capture point has to move — enumerate `sessionStorage`/`localStorage` key
*names* on the page to find where the token went instead.
