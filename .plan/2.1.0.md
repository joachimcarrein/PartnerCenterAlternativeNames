# v2.1.0 — Shift+click inverts the customer-name link behaviour

**Status: implemented and live-tested against the real Partner Center app — confirmed working.**

## Goal

Today the customer-name click target is controlled by one setting,
`keepDefaultLinkBehaviour` (the "Keep default link behaviour" checkbox in the
popup):

- Unchecked (default): click → Service management.
- Checked: click → Admin relationships.

Add a **temporary override**: holding **Shift** while clicking flips whichever
behaviour the checkbox currently selects, for that one click only. The setting
itself is not changed.

| Setting (checkbox) | Plain click | Shift+click |
|---|---|---|
| Unchecked (default) | Service management | Admin relationships |
| Checked | Admin relationships | Service management |

This is a straight inversion: `goToServiceManagement = (keepDefaultLinkBehaviour === event.shiftKey)`.
Verified against the four cells above — `false===false→true`, `false===true→false`,
`true===false→false`, `true===true→true` — all match.

---

## Feasibility

Yes. The existing capture-phase click listener
([content.js:335-347](../content.js#L335-L347)) already resolves a click down
to a `tenantId` via `findNameButtonClick(path)` before deciding whether to
redirect. `MouseEvent.shiftKey` is a native, always-present boolean on the
same `click` event object already being inspected — no new listener, no new
permission, no change to `findNameButtonClick()` or `redirectToServiceManagement()`.

The one behavioural change: today the handler returns immediately when
`keepDefaultLinkBehaviour` is `true`, *before* even resolving `tenantId`
(cheap early exit). That short-circuit has to move — the handler must resolve
`tenantId` unconditionally now, because Shift can flip the outcome in either
setting state. This is a negligible cost (composedPath walk on a click event),
not worth preserving the old shortcut at the expense of correctness.

## Changes by file

### 1. `content.js`

Replace the early-return branch with a comparison against `event.shiftKey`:

```js
document.addEventListener(
  'click',
  (e) => {
    const path = typeof e.composedPath === 'function' ? e.composedPath() : [];
    const tenantId = findNameButtonClick(path);
    if (!tenantId) return;
    // Shift held inverts whichever target the setting currently selects,
    // for this one click only — the stored setting itself is never touched.
    const goToServiceManagement = keepDefaultLinkBehaviour === e.shiftKey;
    if (!goToServiceManagement) return; // let native navigation proceed (-> Admin relationships)
    e.preventDefault();
    e.stopImmediatePropagation();
    redirectToServiceManagement(tenantId);
  },
  { capture: true }
);
```

Notes:
- `keepDefaultLinkBehaviour === e.shiftKey` relies on both sides being real
  booleans (`loadNavSetting()` already coerces the stored value to boolean;
  `MouseEvent.shiftKey` is always boolean) — no `Boolean(...)` cast needed.
- No change to `findNameButtonClick()` or `redirectToServiceManagement()`.
- Update the block comment above the listener (currently describes only the
  checkbox, [content.js:272-296](../content.js#L272-L296)) to document the
  Shift inversion and the truth table, so a future reader doesn't have to
  reverse-engineer the `===`.

## Edge cases / notes

- **Shift is read live per-click**, never persisted — closing the popup,
  reloading the page, or reopening the tab has no memory of a past
  Shift-click. Only the checkbox setting persists.
- **Ctrl/Cmd+click does NOT open a new tab — live-tested and confirmed.**
  The original assumption here (that Ctrl+click "normally opens the
  customer in a new background tab via the browser's own handling of the
  underlying element") was wrong: the customer name is a custom
  `<customersvcadmin_he-button>`, not a real `<a href>`, so there's no href
  for the browser to open in a new tab. Ctrl+click behaves identically to a
  plain click (redirects to Service management when the setting is
  unchecked) — this is pre-existing behaviour from 2.0.3, unrelated to and
  unchanged by the Shift feature, since the listener never inspected
  `ctrlKey`/`metaKey` in the first place. Middle-click was not verified
  (test tooling had no middle-click primitive) but is expected to behave
  the same way for the same reason.
- **Shift+click still only affects *that specific click*** on the name
  button — same scoping as the existing feature. It does not make the
  left-nav "Admin relationships" link inside a customer's detail view
  Shift-sensitive; that link was never intercepted and still isn't.
- **No new storage key, no new permission.** Purely a same-click read of
  `event.shiftKey` inside the existing listener.
