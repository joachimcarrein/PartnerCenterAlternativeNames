# v2.2.0 — the extension says when the column is degraded

**Status: implemented and LIVE-TESTED against the real Partner Center app.**
All 12 files below are done, the version is bumped to 2.2.0, the changelog
entry is in, and the test suite is green at **171 assertions** (60 → 171) with
all **27 mutations** confirmed caught.

Every item on the live checklist passed, with check 6 replaced by two narrower
non-destructive checks (see **Live test**). The live test earned its keep: it
found a genuine bug no unit test had caught — the grace escalation never
re-rendered the column, so the degraded tooltip never appeared at all — plus
two smaller surface problems. All three fixed, with tests.

## Why this release exists

2.1.1 degraded **7 of every 10 rows to "Unknown" while reporting success**,
and nothing anywhere said so:

- `loadDomainData()` returns `domainMap.size > 0 || displayNameMap.size > 0`
  ([content.js:662](../content.js#L662)), so 71 healthy domains were enough to
  set `loadState = 'ready'` even though the display-name half had fetched
  nothing at all.
- `rebuildCache()` computes `ok = !!(fresh || names)`
  ([content.js:675](../content.js#L675)), so the popup's **Rebuild local
  cache** reported a green "Cache rebuilt — 71 domain(s), 0 name(s)." for a
  rebuild in which one half hard-failed.
- The popup's cache line ([popup.js:48](../popup.js#L48)) did print
  `0 display name(s)`, but `0` there is indistinguishable from "this partner
  has no delegated-admin customers", carries no timestamp, no reason and no
  remedy, and is buried in a line the user has no reason to read.

The bug was found only because a human noticed the column looked wrong and
said so. `.plan/2.1.1.tests.md` closed with the conclusion that **no unit test
catches this class of failure — only a health signal does.** This is that
signal.

The theme of the release, in one sentence: **know what you actually got, and
say so.** Every change below follows from that.

## What the user gets

1. **A warning in the popup** when a half of the data could not be loaded —
   naming which half, why, when, and what to do about it. Invisible when
   everything is fine, so it stays worth reading.
2. **A `!` on the toolbar icon** for the affected tab, so the user does not
   have to open the popup to find out. This is the part that would have caught
   2.1.1 the same day.
3. **An honest rebuild result.** "Cache rebuilt — 71 domain(s); display names
   failed (sign-in token expired)" instead of a green tick.
4. **A cell that admits it does not know.** A row showing "Unknown" because a
   lookup failed gets a tooltip saying so, distinct from a row that genuinely
   has no domain and no display name (constraint 5 — non-transacted customers
   legitimately have neither).

## Design: `content.js` records facts, `popup.js` judges them

The split matters, and it is the one architectural decision in this release:

- `content.js` writes **facts only** — what was attempted, what came back, how
  many rows resolved. No verdicts, no user-facing strings.
- `popup.js` owns the **single** `assessHealth()` function that turns those
  facts into a level and a message.

Why not compute the verdict in `content.js` and store it? Because there is no
module system (CLAUDE.md, Repository conventions), so a verdict computed in
`content.js` and rendered in `popup.js` would need its wording duplicated in
both files and would drift. Facts do not drift. It also puts the testable pure
function in `popup.js`, which `tests/helpers/load-iife.js` already loads.

### The health record

New `chrome.storage.local` key, `loadHealth`:

```js
{
  at: 1757505125990,          // epoch ms — when this state was FIRST observed
  domains: { source: 'cache', count: 71 },
  names:   { source: 'failed', count: 0, reason: 'no-token' },
  rows:    { injected: 10, resolved: 3 },
  tokens:  { partnerCenter: true, gdap: false }
}
```

| Field | Values | Meaning |
|---|---|---|
| `source` | `'cache'` | served from `domainCache` / `displayNameCache`, no fetch attempted |
| | `'fetch'` | fetched successfully this load (a `count` of `0` here is a **valid** result — see below) |
| | `'partial'` | multi-page fetch failed part-way; `count` is what arrived |
| | `'awaiting'` | names only: no GDAP token yet, still inside the grace window |
| | `'failed'` | attempted and failed; `reason` says how |
| `reason` | `null`, `'no-token'`, `'auth'`, `'network'`, `'http'`, `'parse'` | non-null only for `'partial'`, `'awaiting'` and `'failed'` |
| `rows` | counts from the most recent injection pass | `resolved` = rows showing an override, a domain or a display name; i.e. anything but `Unknown`/`—` |
| `tokens` | booleans | same contract as `getTokenStatus()` — never the token values |

**Privacy audit.** The record holds counts, booleans, an epoch timestamp and a
reason enum. No tenant IDs, no domains, no display names, no custom names, no
tokens, no token prefixes. It is never exported (`doExport()` reads only
`OVERRIDE_KEY`) and nothing new leaves the machine.

**`count: 0` with `source: 'fetch'` is a success.** A partner with no
delegated-admin customers legitimately has zero display names. Today both
fetchers destroy that distinction — `fetchDisplayNames()` ends with
`return Object.keys(out).length ? out : null`
([content.js:596](../content.js#L596)), and `loadDomainData()` tests
`if (fresh && Object.keys(fresh).length)` — so a legitimate empty result is
indistinguishable from a hard failure. Harmless until now; with a badge
attached to it, it becomes a false alarm. §1 fixes it.

### Why persisted rather than queried live from the tab

The popup could ask the open tab for its in-memory state, as it already does
for rebuild (`chrome.tabs.sendMessage`). Rejected:

- It gives nothing when no GDAP tab is open — which is most of the time the
  popup is opened, and exactly when a user who noticed a wrong column goes
  looking for an explanation.
- The badge needs the state anyway, and a badge fed from a different path than
  the popup can disagree with it.
- The orphaned-content-script case (extension reloaded, tab not refreshed)
  already forces the rebuild flow to carry a fallback branch; a second one
  would be a second thing to get wrong.

Persisted state can be stale, which is the price. It is paid honestly by
rendering `at` in the popup, and by clearing `loadHealth` alongside the cache
keys so it can never describe data that has been deleted.

## Feasibility

No new permissions. `chrome.action.setBadgeText` needs only the `action` key,
which `manifest.json` already declares. No new host permissions, no new
content script, no change to the world split or to the bridge protocol.
`docs/privacy.html` needs one bullet (it enumerates what is stored) but no
change of substance, because nothing new is transmitted.

The one genuine risk is false positives, which is §A below.

## Changes by file

### 1. `content.js` — fetch results carry a reason

Both fetchers currently answer "data or `null`", collapsing five outcomes into
one. Change both to return a result object:

```js
// { ok, data, count, partial, reason, pages }
//   ok:      the request sequence completed (count may be 0 — a valid answer)
//   partial: some pages arrived, then one failed
//   reason:  null when ok && !partial
```

- `fetchAllDomains()` ([content.js:431](../content.js#L431)) — replace each of
  the four `return null` exits with a reason: `'no-token'` (no
  `AuthContextData`), `'network'` (`!resp.ok`), `'auth'` (401), `'http'`
  (other non-OK), `'parse'` (bad JSON). When a page past the first fails,
  return what arrived with `partial: true` instead of discarding it.
- `fetchDisplayNames()` ([content.js:558](../content.js#L558)) — same reasons.
  Its loop already `break`s on failure and returns partial data; today that
  partial result is **indistinguishable from a complete one and gets cached
  for 30 days as authoritative**. Now it is flagged.
- `fetchSingleDomain()` ([content.js:486](../content.js#L486)) — left alone.
  It has one caller, which only cares whether a domain came back.

Three call sites update: `loadDomainData()`, `rebuildCache()`,
`maybeRecoverDisplayNames()`.

**New rule, and the reason it exists: a partial result is used in memory but
never written to cache.** This is fix 1 of 2.1.1 ("an empty cache half is not
data") extended one step — a half-populated half is not complete data either,
and persisting it under a 30-day TTL freezes the damage exactly as the `{}`
poisoning did. Showing partial data beats showing none, so it still renders;
it just does not get to become the cached truth.

### 2. `content.js` — the health record, written only when it changes

```js
function healthSignature(h) {
  return [h.domains.source, h.domains.count,
          h.names.source, h.names.count, h.names.reason || '-',
          h.rows.injected, h.rows.resolved].join('|');
}
```

**`at` is deliberately not in the signature.** Include it and every call
differs from the last, the dedupe never fires, and an injection pass on every
debounced mutation (scroll, page, search) turns into a storage write on every
debounced mutation. The consequence of leaving it out is that `at` means "when
this state was first observed" rather than "last checked", which is the more
useful of the two anyway — it dates the *problem*, not the poll.

`writeHealth(record)` compares signatures, returns early when unchanged, and
otherwise writes `loadHealth` **and** messages `background.js` for the badge
(one trigger, so the badge and the popup can never disagree). The same
signature trick already appears in `renderCell()` as `span.dataset.rendered`.

Called from: the end of `loadDomainData()`, `rebuildCache()`, a successful
`maybeRecoverDisplayNames()`, the grace-window timeout (§A), and the end of
`injectRows()`/`refreshRowText()` for the row counts.

`ALTNAME_CLEAR_ALL` clears the in-memory record and sends a badge-clear —
storage is already wiped by the popup at that point.

### 3. `content.js` — row-level truth

In `injectRows()` ([content.js:899](../content.js#L899)), while walking rows
that pass `UUID_RE`, count `injected`, and count `resolved` when
`effectiveInfoForTenant(id).text` is not in `PLACEHOLDERS`. Skip the whole
count while `loadState === 'pending'` — every row reads `Loading...` then, and
recording `0 of 10` would be a lie for the ~1s before data lands.

This is the number that actually matters. "3 of 10 rows resolved" needs no
knowledge of the extension's internals to be alarming, and it is precisely
what a user staring at the 2.1.1 grid was seeing. It is also the only signal
that does not depend on guessing an expected total: the two APIs cover
different, overlapping customer populations, so "0 of 71" — names measured
against domains — would be misleading rather than informative.

### 4. `content.js` — the cell admits uncertainty

`naturalInfoForTenant()` ([content.js:724](../content.js#L724)) keeps
returning the text `'Unknown'`, but gains a flag when the names half is
`'failed'`/`'partial'`: the value span then gets
`title = 'Display-name lookup failed — open the extension popup.'`.

Text unchanged on purpose. Inventing a fourth placeholder would ripple into
`PLACEHOLDERS`, `beginEdit()`'s "is this a real value" test and
`applyEdit()`'s equal-to-natural comparison, for a distinction the tooltip
carries at zero risk.

### 5. `background.js` — the toolbar badge

A second `onMessage` listener for `{ type: 'ALTNAME_HEALTH', level }`:

```js
const tabId = sender.tab && sender.tab.id;      // tab-scoped, never global
chrome.action.setBadgeText({ text: level === 'warn' ? '!' : '', tabId });
chrome.action.setBadgeBackgroundColor({ color: '#a4262c', tabId });
```

`#a4262c` is the error red already used by `popup.html` and `content.js`.

**Tab-scoped, not global.** The tokens live in one tab's `sessionStorage`, so
the condition is per-tab; a global badge would also outlive the tab that
earned it. *To verify during the live test:* Chrome documents tab-specific
`action` state as reset on navigation — confirm a badge set on the GDAP page
is gone after navigating that tab elsewhere, and add an explicit clear if not.

The existing listener returns `false` for anything that is not `PC_FETCH`, so
a second listener is safe; messages from `content.js` via
`chrome.runtime.sendMessage` reach the worker and not the sender's own
listener, so there is no crosstalk with the popup's `chrome.tabs.sendMessage`
handler.

### 6. `popup.js` — `assessHealth()`, and honesty in the rebuild

Add `HEALTH_KEY = 'loadHealth'` to `CACHE_KEYS`
([popup.js:18](../popup.js#L18)) — it is derived data with a server-side
source of truth, so rebuild must clear it. The comment above that line
(`Never add OVERRIDE_KEY to this list`) stands unchanged and gets a test (§T5).

The pure core:

```js
// record: the stored loadHealth, or undefined on a fresh install
// counts: { domains, names } from the cache keys
// -> { level, headline, detail, hint }   level: 'ok'|'pending'|'warn'|'unknown'
function assessHealth(record, counts) { … }
```

| Situation | Level | Headline |
|---|---|---|
| no record | `unknown` | "No status yet — open the Partner Center page." |
| both halves `cache`/`fetch` | `ok` | (banner hidden) |
| names `awaiting` | `pending` | "Display names are still loading." |
| one half `failed`/`partial` | `warn` | "Display names could not be loaded." / "Customer domains could not be loaded." |
| both `failed` | `warn` | "No customer data could be loaded." |
| rows incomplete **and** a half failed | `warn` | as above, plus "3 of 10 rows on the last page showed no name." |
| rows incomplete, both halves fine | `ok` | banner hidden; the row line still shows in the detail |

That last row is the deliberate line between an alarm and a fact. A row that
resolves to nothing while both fetches genuinely succeeded is a customer with
no domain and no display name — legitimate under constraint 5, and badging it
would train the user to ignore the badge.

Reasons become plain words, no jargon and no enum leaking into the UI:

| `reason` | shown as | hint |
|---|---|---|
| `no-token` | "the page did not provide a sign-in token" | "Refresh the Partner Center tab, then use Rebuild local cache." |
| `auth` | "the sign-in token had expired" | same |
| `network` | "the request could not be sent" | "Try Rebuild local cache." |
| `http` | "Microsoft's API returned an error" | "Try Rebuild local cache; Microsoft's API may be having trouble." |
| `parse` | "Microsoft's API returned something unexpected" | same |

`refreshStatus()` reads `loadHealth` alongside the cache keys, renders the
banner (or hides it), and appends the compact form to the existing cache line:
`71 domain(s) / 0 display name(s) · display names failed · expires 10/10/2026`.

`doRebuild()` ([popup.js:268](../popup.js#L268)) reports per half from the new
`rebuildCache()` result instead of a flat count, and is no longer allowed to
show `'ok'` when a half failed. **This is the 2.1.1 mis-report itself, fixed.**

## A. The false-positive risk, and the grace window

The one thing that can make this release worse than no release is a badge that
cries wolf. There is exactly one such case, and it is common.

`content.js` runs at `document_idle`, and the GDAP token only exists once the
page itself has called that API — which is why `maybeRecoverDisplayNames()`
exists at all. So `'no-token'` at first load is very often **not yet failed**,
merely **not yet arrived**.

Mitigation, in two parts:

1. `source: 'awaiting'` (level `pending`, **no badge**) is recorded when the
   names half has no token, rather than `'failed'`.
2. A single `setTimeout` — **15s**, cancelled by a successful recovery —
   escalates `'awaiting'` to `'failed'` and writes again. Without the timer, a
   genuinely broken state stays quietly "pending" forever whenever the page
   never calls the GDAP API again.

15s is a guess and is written down as one. The grid's own data comes from that
same API, so the token should be captured at page load, well before
`document_idle` — consistent with 2.1.1's live result, where a reload produced
correct names immediately. **The live test must confirm 15s never fires on a
healthy page**; if it does, the number moves, not the design.

## Rejected alternatives

| Alternative | Why not |
|---|---|
| Store a computed verdict instead of facts | Two files would have to agree on wording with no module system to share it. Facts do not drift. |
| Popup queries the tab live for state | Nothing when no tab is open — the exact moment the user goes looking. And it feeds the badge from a second path that can disagree. |
| A fourth placeholder (`'Unknown?'`) in the cell | Ripples into `PLACEHOLDERS`, `beginEdit()` and `applyEdit()`'s equal-to-natural test for what a tooltip carries safely. |
| A global badge | The condition is per-tab (per-`sessionStorage`), and a global badge outlives the tab that earned it. |
| Warn on any unresolved row | Non-transacted customers legitimately have no domain and no display name (constraint 5). Badging that teaches the user to ignore the badge. |
| Expected-total ratio ("0 of 71") | The two APIs cover different, overlapping populations; names measured against domains is a misleading denominator. |
| Notify via `chrome.notifications` | A new permission and an interruption, for something the toolbar icon can say quietly. |

## Edge cases

- **Fresh install / upgrade from 2.1.1** — no `loadHealth` key. `unknown`, no
  badge, banner explains rather than warns. Must not read as a failure.
- **Pure cache hit** — both halves `'cache'`, nothing fetched, no token needed.
  `ok`. The absence of a token must not be a warning when nothing was asked of
  it.
- **Rebuild with no GDAP tab open** — popup clears the cache keys including
  `loadHealth`, no tab replies, so the state legitimately becomes `unknown`.
  The popup already says "Cache cleared. Open the Partner Center tab…".
- **Orphaned content script** (extension reloaded, tab not refreshed) — no
  reply to the rebuild message, `loadHealth` stays cleared, `unknown`. Correct:
  nothing is known.
- **Both halves served from cache while the cache is stale-but-unexpired** —
  `ok`, which is right; the health record describes the load, and a load that
  correctly used valid cache did not fail.
- **`ALTNAME_CLEAR_ALL`** — badge cleared, record gone, `loadState` back to
  `'pending'`. Blank-install look, no leftover `!`.
- **Two GDAP tabs open** — each writes the same shared `loadHealth` (last
  write wins), but badges are per-tab, so a healthy tab shows no `!` while a
  broken one does. Accepted: the popup is one shared surface and cannot show
  two states. Worth a line in the plan rather than a mechanism.

Per CLAUDE.md, the pure logic here is testable and gets assertions in the same
change; the DOM and API parts do not and are named as such.

**T4 — the fetch result objects.** Each reason returned for the matching

**T5 — the constraint-9 guard.** Assert `OVERRIDE_KEY` is not in `CACHE_KEYS`

**Mutations to run** (every new test must be shown to fail):

| Mutation | Must break |
|---|---|
| Add `at` to `healthSignature()` | T2 dedupe |
| `assessHealth()` returns `ok` when one half failed | T1 truth table |
| Treat `source:'fetch', count:0` as failed | T1 legitimate-zero case |

Then restore each file and verify byte-identical with `cmp` plus `node --check`.

All four go on the live-test checklist below instead.

**Live-test checklist** (against the real Partner Center app — the release is
not finished until these are ticked, and the Status line must say which were
run):

1. Healthy load: no badge, banner hidden, cache line shows both counts.
2. Healthy load: the 15s escalation never fires.
3. Break the GDAP half deliberately (e.g. force `getGdapToken()` to return
   `null`): `!` appears, banner names display names, hint is actionable.
4. Rebuild with that break in place: no green tick; the message names the
   failed half.
5. Navigate the tab away: badge gone.
6. Clear all: badge gone, blank-install look.

## Not in scope

- **Persisting `fetchSingleDomain()` results.** Deliberately unfixed in 2.1.1
  ([.plan/2.1.1.md](2.1.1.md), "Not fixed") because a 1-entry cache can
  masquerade as complete — the same class as the `{}` poisoning. The health
  record makes a safe version conceivable (a per-entry `source`), but that is
  a cache-shape change and belongs in its own release.
- **Retrying a failed half on a timer.** The signal comes first; automatic
  recovery on top of a signal nobody has looked at yet is guesswork.
- **Surfacing health on the page itself** (a banner above the grid). The
  toolbar badge is the cheap 90%; a page banner means injecting chrome into
  Microsoft's UI, which this extension has so far only done for one column.
- **Shadow DOM / injection tests.** Unchanged from
  [.plan/2.1.1.tests.md](2.1.1.tests.md): needs jsdom, and its shadow-root
  fidelity would not match Partner Center's markup, so the test would exercise
  the fixture.

## Scope note

§1's partial-result handling (`partial: true`, and not persisting partials) is
the one part that could be dropped for a smaller release: it is a latent bug
rather than the reported one. It is included because it is the same mistake as
the 2.1.1 `{}` poisoning one page further on — a half-populated half of the
cache freezing under a 30-day TTL — and because the plumbing it needs is
already being built for the reasons. Say so if you would rather ship the
signal alone; nothing else in the plan depends on it.

# Implementation record

Written after the fact. The design above is unchanged except where noted here.

## Deviations from the design, and why

1. **`healthSignature()` includes `domains.reason` as well as `names.reason`.**
   §2's code block listed the reason for the names half only. That asymmetry
   is a real (if small) correctness gap: a domains half that fails with
   `network` and then, on a rebuild, with `auth` keeps `source: 'failed'` and
   `count: 0`, so the signature would not change, the record would not be
   rewritten, and the popup would show the stale reason with the wrong remedy.
   Both reasons are in the signature now. `at` and `tokens` remain out, which
   is the part that was load-bearing.

2. **The row line reads "Only 3 of 10 rows … showed a name", not "3 of 10 …
   showed no name".** §6's example sentence was inverted relative to its own
   field definition (`resolved` counts rows that *do* show something, so
   `{injected: 10, resolved: 3}` means seven showed nothing). The field
   definition won.

3. **`describeRebuild()` refuses to interpret a reply it cannot read.** §6 only
   required honest per-half reporting. A reply whose halves are not the new
   `{ok, count, partial, reason}` shape (a malformed message, or a content
   script older than 2.2.0, which answered with the maps themselves) would
   otherwise have every half read as `ok: undefined` → "failed", inventing a
   specific failure for a rebuild that may well have worked. It now says the
   result could not be read. Note this path is close to unreachable in
   practice: reloading the extension severs the orphaned content script's
   message port, so that case lands in `doRebuild()`'s existing
   `chrome.runtime.lastError` branch instead.

Two smaller notes, both consistent with the design rather than departures from
it:

- **`refreshRowText()` does not repeat the row tally**, though §2 listed it as
  a call site. The tally is derived from in-memory state, not the DOM, so a
  second pass over the same rows computes identical numbers and would be
  deduped away by `healthSignature()` anyway. Counting in `injectRows()` alone
  is the same result with one fewer place to keep in step.
- **`content.js` computes a badge level**, in `badgeLevel()`. That is the one
  judgement outside `popup.js`, and it is unavoidable: the badge needs a
  boolean and the worker cannot read the popup's wording. It is deliberately
  the *narrowest* judgement possible — on/off, agreeing with `assessHealth()`'s
  warn rule by construction — and it carries a comment saying so.

## Live test

Run against the real Partner Center app on a tenant with 71 domains / 88 GDAP
display names, 6 custom names, 10 rows per page. Counts only below — no tenant
IDs, customer names or domains, per the repository rule.

**Check 1 — healthy load (warm cache): PASS.** `Health recorded:
cache|71|-|cache|88|-|0|0` then `…|10|10`. Banner hidden, no badge, cache line
correct. Two storage writes across two MutationObserver fires and ten cell
injections — the `healthSignature()` dedupe holds against real markup.

**Check 2 — the 15s window never fires on a healthy page: PASS.** Confirmed
cold (`Cache MISS`, both halves fetched): the bridged GDAP token arrived
*before* `fetchDisplayNames()` ran, so the names half went straight to `fetch`
and the timer never armed. `Cached 71 domains and 88 names` confirms the
complete-fetch-is-persisted rule. The `awaiting` → recovery variant was not
observed on this tenant because the token consistently arrives first; the
timer's arming and escalation were exercised by check 3 instead.

Also confirmed live, and worth recording: `CustomerSvcAdminKey missing from
sessionStorage — trying the bridged token.` The 2.1.1 root cause is still
present, the page's own `accesstokens?…CustomerSvcAdminGdap` call returns
**400**, and the bridge is carrying the entire display-name half. Constraint 4
is right to treat the sessionStorage key as a fast path only.

**Check 3 — GDAP half broken (`getGdapToken()` forced to `null`): PASS after a
fix.** `fetch|71|-|awaiting|0|no-token|10|4`, quiet; then at 15s `Grace window
elapsed with no GDAP token — escalating to failed.` and
`…|failed|0|no-token|10|4`. Red `!` on the toolbar icon. Popup banner correct
in wording, reason, row count and hint. **The tooltip did not appear** — see
the bug below. Re-tested after the fix: the tooltip now appears on the
`Unknown` cells (and only on those) once the escalation fires.

**Check 4 — rebuild with the break in place: PASS.** Reported the failed half
rather than a green tick.

**Check 5 — badge cleared on navigation: PASS.** Navigating the tab away
removes the `!`, so Chrome does reset tab-specific `action` state as
documented and no explicit clear is needed.

**Check 6 — replaced.** As designed ("clear all: badge gone, blank-install
look") it mostly re-tested pre-2.2.0 behaviour this release never touched:
`loadState = 'pending'`, the in-memory resets and the confirm dialog are all
unchanged, and `cancelNamesGrace()` is belt-and-braces because the timer
already early-returns on a null record (which *is* unit-tested). Against that,
it destroys `nameOverrides` — the one key with no server-side source of truth
— and makes the verification depend on the import path working. Only two facts
in it were new, and both were obtained without deleting anything:

- **6a — the badge clears in place once the problem is fixed: PASS.** With the
  `!` showing, `clearCache()` + reload produced `fetch|71|-|fetch|88|-` and the
  badge disappeared **without navigating**. That is the same `sendBadge('ok')`
  call `ALTNAME_CLEAR_ALL` makes, so the clear-all badge behaviour is covered
  by proxy. Note this check was **missing from the checklist above** — it only
  asked whether the badge appears and whether navigation clears it, never
  whether it goes away once the condition resolves, which is the case a user
  actually hits. A badge that never clears would be worse than no badge.
- **6b — a fresh install reads as grey, not as a failure: PASS.**
  `clearCache()` (which deliberately omits `nameOverrides`) followed by opening
  the popup without a reload shows the grey "No status yet — open the Partner
  Center page." — not red, not amber. That is the fresh-install and
  upgrade-from-2.1.1 state from **Edge cases** above, and the one the plan
  insisted "must not read as a failure".

The destructive clear-all was therefore **deliberately not run**, and nothing
about it is left unverified except the paths this release did not change.

### The bug the live test found

The cells are rendered while the names half is still legitimately `awaiting`,
so `degraded` is correctly `false` and they carry no tooltip. The 15s
escalation then updated the record, the badge and the popup — but **nothing
re-rendered the column**, and on an idle page no grid mutation ever arrives to
do it. The tooltip therefore never appeared at all.

`rebuildCache()` and `maybeRecoverDisplayNames()` both re-render after writing
health; `startNamesGrace()` was the one path that did not. Fixed by re-rendering
there too, with a test that fires the timer against a stub grid and asserts the
resulting cell carries the tooltip (mutation N1).

**No unit test could have caught this as originally written**, and it is worth
being precise about why: every individual piece was correct and tested — the
record escalated, `namesLookupFailed()` returned true, `renderCell()`'s
signature included the flag and produced the tooltip. What was missing was a
*trigger*, and nothing in the suite asserted that a health change reaches the
DOM. That is the same shape as the 2.1.1 lesson one level up: the parts were
right, the wiring between them was not.

Two smaller things the live test also surfaced, both fixed:

- **The banner repeated itself.** Headline "Display names could not be loaded."
  followed by detail "Display names could not be loaded — the page did not
  provide a sign-in token." When only one half is broken the headline already
  names it, so the detail now leads with the reason ("The page did not provide
  a sign-in token."). With *both* halves broken the per-half labels stay,
  because there the headline cannot disambiguate (mutations N2, N3).
- **A popup open during the amber phase never updated.** It would sit on
  "Display names are still loading." ~15s after the load had actually failed.
  `popup.js` now refreshes on a `loadHealth` change, narrowed to that key so
  an import or a setting toggle does not re-read all five (mutations N4, N5).
